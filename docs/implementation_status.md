# Implementation Status Report

**Purpose:** an honest, evidence-based inventory of everything that currently blocks this
system from processing a real enquiry end-to-end, grouped by priority. Generated by
inspecting the repository and, where a static read wasn't conclusive, by actually running
the test suites and a live server process. **No files were modified to produce this report.**

**Bottom line:** the system is **not runnable end-to-end today**. The architecture,
schemas, database layer, tool framework, and the Planner → Executor → Verifier →
Orchestrator control flow are fully implemented and pass their own test suites (using fake
adapters / mock tools) — but every real integration point a live request would actually
have to cross is either an intentional stub or unwired:

- No LLM provider is implemented, so nothing that calls a model can run.
- All 4 tools intentionally `raise NotImplementedError` (per explicit prior instruction),
  so the Executor cannot complete a single real tool call.
- The one endpoint that would submit an enquiry (`POST /api/runs`) isn't wired to the
  (fully working) Orchestrator, doesn't accept a request body, and currently crashes with
  an unhandled `500` rather than its intended `501`.
- The 45-run harness and the 3-case adversarial script both refuse to run because their
  fixture files are still empty, pending the brief's real enquiry samples.
- A currently-live config bug (blank `DATABASE_URL=` in `.env`/`.env.example`) breaks
  database access outright and is responsible for 14 real, reproduced test failures.

Each item below is verified against the current code, not inferred from comments alone.

## Critical — nothing works end-to-end until these are resolved

### 1. No concrete `ModelAdapter` implementation exists
**File:** `server/app/llm/factory.py:24-34`

```python
def build_adapter(settings: Settings) -> ModelAdapter:
    raise NotImplementedError(
        f"No ModelAdapter implementation exists yet for MODEL_PROVIDER="
        f"{settings.model_provider.value!r}. Add app/llm/<provider>_adapter.py "
        f"and wire it in here."
    )
```

The provider-agnostic `ModelAdapter` interface (`server/app/llm/base.py`) and the calling
code in `agent/planner.py`, `agent/verifier.py`, and `agent/orchestrator.py` are all fully
implemented and depend only on this abstraction — but there is no OpenAI/Anthropic/Ollama
implementation of it anywhere in the repo (only `base.py`, `factory.py`, `pricing.py`
exist under `server/app/llm/`). **Every code path that needs an LLM call fails immediately**,
regardless of whether an API key is configured.

### 2. All four tools are intentional stubs — the Executor cannot complete a plan
**Files:** `server/app/tools/parse_enquiry.py:39`, `lookup_jurisdiction_rule.py:43`,
`score_lead.py:42`, `write_record.py:47`

Each tool's `run()` validates its input (via `Tool.execute()`) and then unconditionally
`raise NotImplementedError`. This was an explicit, deliberate requirement of an earlier task
("Every tool should simply raise `NotImplementedError` after validating its input") — it is
not a bug, but it means **no plan can ever finish executing**: the Executor's own contract
(`agent/executor.py`) correctly converts this into a structured `ExecutionResult(error=...)`
rather than crashing, but the pipeline can never produce a `final_record` today.

### 3. `POST /api/runs` isn't wired to the Orchestrator, and currently 500s instead of 501ing
**File:** `server/app/api/routes_runs.py:19-39`

```python
class CreateRunRequest:
    # TODO(api/routes_runs): replace with a proper Pydantic request model,
    pass

@router.post("", response_model=RunResult)
def create_run(
    db: Session = Depends(get_db),
    adapter: ModelAdapter = Depends(get_adapter),
    settings: Settings = Depends(get_app_settings),
) -> RunResult:
    raise HTTPException(status_code=501, detail="Not implemented yet.")
```

Two distinct problems, confirmed by actually starting the server and calling the endpoint:

- `CreateRunRequest` is an **empty placeholder class, not a Pydantic model**, and isn't even
  used as a parameter on `create_run()` — there is currently no way to submit `enquiry_text`
  to this endpoint at all, even once the 501 is removed.
- The intended `501` response is **never actually returned**. `Depends(get_adapter)` calls
  `llm/factory.py::get_adapter()`, which raises `NotImplementedError` (see Critical #1)
  *during FastAPI's dependency resolution* — before the route body's `HTTPException(501)`
  ever executes. Verified live:

  ```
  $ curl -X POST http://127.0.0.1:8899/api/runs -d '{"enquiry_text":"hi"}'
  Internal Server Error          # HTTP 500, not 501
  ```

  Server log confirms the uncaught exception:
  ```
  File ".../app/api/deps.py", line 20, in get_adapter
      return _get_adapter()
  File ".../app/llm/factory.py", line 46, in get_adapter
      return build_adapter(get_settings())
  NotImplementedError: No ModelAdapter implementation exists yet for MODEL_PROVIDER='openai'...
  ```

  This is worth fixing distinctly from #1: even after a real adapter exists, this endpoint
  still needs a real request-body model and an actual call into `Pipeline.run()` — none of
  that wiring exists yet, despite `agent/orchestrator.py::Pipeline` being fully implemented
  and tested in isolation.

### 4. Evaluation harness and adversarial script cannot run — fixture data is empty
**Files:** `evaluation/fixtures/enquiries.json`, `evaluation/fixtures/adversarial_enquiries.json`

```json

   (per docs/Trial_Brief_Paul_Detablan.md section 3.1, ...)", "enquiries": [] }
```

Both fixture files are placeholders waiting on the brief's real data ("I will supply 15
enquiry samples on the Monday morning" / 3 adversarial cases). `evaluation/harness.py` and
`evaluation/adversarial.py` are both otherwise fully implemented, but `run_harness()`

```python

    raise ValueError(
        "No enquiries to run: evaluation/fixtures/enquiries.json is empty. The 15 real "
        "enquiry samples must be supplied before the harness can run ..."
    )
```

Confirmed by running the evaluation test suite (see "Current test status" below) — every
test that doesn't explicitly inject fake enquiries in-memory fails on this exact check.

### 5. Live config bug: blank `DATABASE_URL=` breaks all database access
**Files:** `.env`, `.env.example` (both contain `DATABASE_URL=` with no value)

`server/app/core/config.py` defines a sensible SQLite default for `database_url`, intended
to apply whenever `DATABASE_URL` is unset. But pydantic-settings treats an env var that is
**present but empty** as an explicit override, not as "unset" — so the default is silently
discarded. Reproduced directly:

```
$ DATABASE_URL= python -c "from app.core.config import Settings; print(repr(Settings().database_url))"
''
```

An empty string is not a parseable SQLAlchemy URL, so any code path that opens a DB session
without an explicit engine override (`db/session.py::build_engine`) crashes with:

```
sqlalchemy.exc.ArgumentError: Could not parse SQLAlchemy URL from given URL string
```

This is not hypothetical — it is the **root cause of 14 currently-failing tests** (2 in
`server/app/tests/unit/test_orchestrator.py`, 12 in `evaluation/tests/test_harness.py` and
`test_harness_integration.py`; see "Current test status"). It also means anyone following the
README's own setup instructions verbatim (`cp .env.example .env`, fill in the API key, leave
everything else as shipped) has a broken database out of the box, independent of any LLM/tool
work. **Fix is trivial** (drop the blank `DATABASE_URL=` line, or make the config layer treat
an empty string the same as unset) but it is currently live and actively breaking things.

### 7. Repair Loop is entirely unimplemented
**File:** `server/app/agent/repair.py:28-51`

```python

    raise NotImplementedError
```

The brief and `docs/architecture.md` §10 both call for exactly one repair attempt before a
failed verification is quarantined. `agent/orchestrator.py` was built to explicitly *not*

straight to `final_status="quarantined"` (never silently dropped, but also never repaired).
This is a real, documented gap rather than a hidden one, but it means a whole pipeline stage
described in the architecture doesn't exist at all yet.

## Medium — would produce misleading results rather than crash

### 11. Jurisdiction rules data is placeholder, not real business data
**File:** `server/app/data/jurisdiction_rules.json`

Only "United Kingdom" and "United States" have entries, and every `handling_note` is the
literal string `"TODO: placeholder rule."` (including the `default` fallback). Once
`lookup_jurisdiction_rule` (#2) is implemented against this file, any enquiry from a country
outside those two — plausible across 15 real samples — will silently fall through to an
equally-placeholder default rule rather than a real one.

### 12. Cost reporting will always be $0.00
**File:** `server/app/llm/pricing.py:19-22`

```python
PRICING_PER_1K_TOKENS: dict[str, dict[str, float]] = {
    # "gpt-4o-mini": {"prompt": 0.0, "completion": 0.0},
    # "claude-3-5-haiku": {"prompt": 0.0, "completion": 0.0},
}
```

`estimate_cost_usd()` itself is fully implemented and correctly, honestly falls back to
`0.0` with a logged warning for any unrecognized model rather than fabricating a number —
but since the pricing table is empty, **every remote model is "unrecognized," so every run's
`total_cost_usd` and the harness's required `mean_cost_usd` metric (docs/architecture.md
§11) will report exactly $0.00** until real per-model prices are filled in.

### 13. Missing provider credentials aren't caught at config-load time
**File:** `server/app/core/config.py:86-92`

```python
@model_validator(mode="after")
def _check_provider_credentials(self) -> Settings:
    # TODO(config): once adapters exist, decide whether missing credentials
    # should raise here (fail fast) or only when that adapter is actually
    # instantiated by llm/factory.py. Left permissive for now ...
    return self
```

A missing `OPENAI_API_KEY` (or equivalent) for the selected `MODEL_PROVIDER` currently
produces no early, clear error — the failure would only surface later, deep inside whatever
adapter eventually gets built. Low effort to add once an adapter exists.

### 14. Two business-rule guardrails live in code, not in the schema (by design, but worth tracking)
**Files:** `server/app/schemas/plan.py:43-47`, `server/app/schemas/verifier.py:24-27`

`Plan` doesn't structurally enforce "`lookup_jurisdiction_rule` and `score_lead` each appear
exactly once" — that's enforced in `agent/planner.py::_check_mandatory_tools()` instead.
`VerifierDecision` doesn't structurally enforce "`reason` non-empty when `passed=False`" —
that's relied on via prompt instruction only, with no code-level validator. Both are
functionally covered today by the modules that call them, but a future direct construction
of either schema (e.g. from a different code path) would not be protected.

### 15. No provider SDK is pinned yet — a real, known dependency gap before deployment
**File:** `server/requirements.txt:13-16`

Deliberately correct today (no adapter exists to import an SDK for), but flagged here as a
concrete pre-deployment action item: whichever provider is chosen needs its SDK added (e.g.
`openai==...` or `anthropic==...`; Ollama needs none, it's called over plain HTTP via the
already-pinned `httpx`), plus the matching `OPENAI_API_KEY`/`ANTHROPIC_API_KEY` secret
provisioned in the deployment environment.

### 16. Docker image has not been built/run in this environment
**File:** `Dockerfile` (root)

Structurally sound (multi-stage: Node build → Python runtime with static files baked in),
but no Docker daemon was available to actually verify `docker build` / `docker run`
end-to-end in this sandbox (noted in an earlier session too). Should be verified once a
Docker-capable environment is available, before relying on it for deployment.

## What already works (for balance)

To be clear about what *isn't* a gap: the following are fully implemented, tested, and
lint-clean, and none of the issues above require redesigning them —

- **Schemas** (`server/app/schemas/`): `Plan`, `VerifierDecision`, `ToolCallTrace`,
  `RunResult`, `ExtractedFields`, `LeadRecord` — all real Pydantic models with validation.
- **Database layer** (`server/app/db/`): models, repository functions (including all the
  harness-specific ones), session management, SQLite WAL mode, duplicate-detection hashing
  (`services/dedupe.py`) — all implemented and tested.
- **Tool framework** (`server/app/tools/base.py`, `registry.py`): base interface, automatic
  registration, deterministic manifest, two-sided validation — fully implemented; only the
  four tools' *business logic* is stubbed (Critical #2), by design.
- **Planner, Executor, Verifier, Orchestrator** (`server/app/agent/`): all four fully
  implemented against `docs/contracts.md`, each with their own unit + integration tests
  using fake adapters / mock tools. The control flow, error handling, and logging are real —
  they simply have nothing real to call yet (Critical #1, #2).
- **Evaluation harness code** (`evaluation/harness.py`, `metrics.py`): fully implemented,
  resumable, with structured JSON + Markdown report generation — blocked only by the empty
  fixture files (Critical #4), not by its own logic.
- **Frontend** (`client/`): fully implemented single-page UI against the documented API
  contracts, with 53 passing tests — correctly built against endpoints that don't work yet,
  by explicit prior scope decision.

## Suggested order of work to reach "runnable"

1. Fix the `DATABASE_URL` blank-string bug (Critical #5) — five-minute fix, unblocks 14
   currently-failing tests immediately.
2. Wire the four read endpoints to their existing repository functions (High #6) — no new
   logic, just response mapping; gives an immediately visible, low-risk win.
3. Choose one LLM provider and implement its adapter (Critical #1) — this is the one piece
   nothing else can route around.
4. Write `parse_enquiry_prompt.py` (High #9) and implement the four tools' real logic
   (Critical #2) — `lookup_jurisdiction_rule` and `score_lead` are pure/deterministic and
   safe to do before the adapter exists; `parse_enquiry` and `write_record` need the
   adapter and repository respectively.
5. Wire `POST /api/runs` to `Pipeline.run()` with a real `CreateRunRequest` model
   (Critical #3) — at this point a real enquiry can flow end-to-end for the first time.
6. Fill in real jurisdiction data and model pricing (Medium #11, #12) so results and cost
   metrics are trustworthy, not just non-crashing.
7. Once the brief's 15 real enquiries + 3 adversarial cases arrive, populate the fixture
   files (Critical #4) and the harness/adversarial script (High #10) can run for real.
8. Implement the Repair Loop (High #7, #8) last — it's the one architecturally-scoped stage
   that the Orchestrator was explicitly built to route around safely in the meantime.
