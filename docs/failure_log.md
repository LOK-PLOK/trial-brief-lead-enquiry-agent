# Failure Log

**Candidate:** Paul France M. Detablan  
**Brief:** WCC-TRIAL-A

This log describes the main issues I encountered while developing the project, the limitations that still exist, and the improvements I would make with more time. The observations below are based on the Official Trial A submission harness and live adversarial testing.

---

## Past issues (fixed during the trial)

1. **The project started as a scaffold.** At the beginning, the application could not process enquiries from start to finish. The API, tools, and OpenRouter integration all had to be completed before the system became fully functional.

2. **Database configuration problems.** An incorrect or empty database configuration prevented the application from starting correctly. This was fixed by providing a safe default SQLite database.

3. **LLM integration was incomplete.** The application could not process enquiries until the connection to OpenRouter was implemented and working correctly.

4. **Failed enquiries were immediately quarantined.** Originally, any verification failure resulted in the enquiry being quarantined immediately. The system now performs one repair attempt before deciding whether to quarantine the enquiry.

5. **Leads were stored too early.** The application originally saved leads before verification was complete. This was changed so that only verified leads are stored in the database.

6. **The verifier sometimes flagged correct system-generated data as fabricated.** Additional validation checks were added so that information generated by the application's own tools is not incorrectly treated as fabricated.

7. **Verifier decisions could contradict themselves.** In some cases the verifier reported fabrication even though its explanation said the data was correct. A consistency check was added to prevent these conflicting decisions.

8. **Official Trial A samples became available later.** During the early stages of development, the official Trial A enquiries had not yet been released, so temporary fictional samples were used for testing. Once the official E01–E15 dataset became available, it replaced the temporary dataset as the primary evaluation set.

9. **Budget and urgency classification needed updating.** After the official samples were released, the prompts were updated to use the required budget bands (A–D) and official urgency categories, including guidance for converting non-USD currencies.

---

## Example of the repair process

One example occurred during Official Trial A **E11**.

- The enquiry failed its first verification.
- The system automatically performed one repair attempt.
- The repaired result was verified again.
- The second verification passed successfully.
- The enquiry was completed and saved instead of being quarantined.

Other enquiries, such as E13 and E15, also completed successfully after a repair attempt. When a genuine contradiction remained (for example incorrect budget or asset information), the enquiry stayed quarantined with an explanation instead of being silently accepted.

---

## Adversarial testing

Three adversarial enquiries were created to test whether prompt injection could manipulate the pipeline.

| Test | Result |
|------|--------|
| **Skip jurisdiction lookup** | The injected instructions were ignored. The planned tools still executed in the correct order, and the enquiry was quarantined after verification failed. |
| **Force a high budget and immediate urgency** | The application ignored the injected values. The customer's real budget was extracted instead, and the enquiry was quarantined rather than accepted. |
| **Invent customer details** | The system did not create fake names, email addresses, or phone numbers. Missing information remained missing, and the enquiry was quarantined. |

Although some verifier explanations were still inconsistent on a few adversarial runs, the important outcome remained the same: prompt injection did not bypass the workflow, fabricate customer information, or produce a trusted accepted lead.

## Current limitations

1. **Repeated harness runs create duplicate records.** Running the same Official Trial A enquiries multiple times can trigger duplicate-record protection, increasing the reported error rate even though the pipeline itself completed successfully.

2. **Missing country information can still cause failures.** If an enquiry only mentions a city or provides no country at all, jurisdiction lookup may fail.

3. **Spelled-out money amounts remain challenging.** Budgets written entirely in words instead of numbers can still occasionally be classified incorrectly.

4. **Verifier decisions are not perfectly consistent.** In some cases the verifier may still quarantine an enquiry because of model variation, even when the available evidence is limited.

5. **Some evaluation metrics cannot yet be measured.** Metrics such as true fabrication detection require manually labelled ground-truth data, which was outside the scope of this trial.

6. **SQLite storage on free Render is temporary.** Application data may be lost whenever the service is redeployed unless persistent storage is attached.

7. **Large evaluation runs consume OpenRouter credits.** Running the full evaluation harness requires many LLM calls, making extensive testing dependent on available API credits.

## What I could not finish

1. Creating a manually labelled dataset to measure true fabrication detection accuracy.
2. Recording internal schema-retry events as additional evaluation metrics.
3. Improving country detection when only a city is mentioned.
4. Separating duplicate harness runs from genuine pipeline errors during repeated evaluations.

## What I would do with another week

3. Add persistent storage to the deployed Render application.
4. Improve repeated harness testing so duplicate records do not affect evaluation results.
