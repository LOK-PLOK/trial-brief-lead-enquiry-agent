# Contracts

This document defines every immutable contract in the system: the exact shape of data crossing a
boundary (Planner ↔ Executor ↔ Verifier ↔ Repair, Tool ↔ Executor, LLM Adapter ↔ agent code,
Repository ↔ agent/API code, API ↔ client, and the database schema itself).

**Status note:** most business-logic function bodies in the scaffold still `raise
NotImplementedError` (see `docs/development-rules.md` — implementation is deliberately not yet
written). That does **not** make the contracts below provisional: the Pydantic schemas
(`server/app/schemas/`), the `Tool` / `ModelAdapter` / repository function signatures, and the
FastAPI route signatures are already committed types. Implementation must satisfy these contracts
exactly, not redesign them. Any change to a contract in this document is an architecture change
and requires the same justification bar as `docs/development-rules.md` demands ("Do not change the
architecture without justification").

Source of truth for each contract (read the code, not just this doc, for the full docstring/TODO
context):

| Contract | Source file(s) |
|---|---|
| Planner | `server/app/agent/planner.py`, `server/app/schemas/plan.py` |
| Executor | `server/app/agent/executor.py`, `server/app/schemas/tool_trace.py` |
| Verifier | `server/app/agent/verifier.py`, `server/app/schemas/verifier.py` |
| Tool interface | `server/app/tools/base.py`, `server/app/tools/registry.py` |
| LLM Adapter | `server/app/llm/base.py`, `server/app/llm/factory.py` |
| Repository | `server/app/db/repository.py` |
| API endpoints | `server/app/api/routes_*.py` |
| Database entities | `server/app/db/models.py` |

## 1. Planner

**Purpose:** Given the raw enquiry text and the current tool manifest, produce a validated,
ordered plan of tool calls. The Planner is a **pure structured-output LLM call — it never executes
anything** (`docs/development-rules.md`: "Planner never executes tools"; `agent/planner.py` must
never import `agent/executor.py` or `tools/`).

### Input

`build_plan(enquiry_text: str, tool_manifest: list[dict], adapter: ModelAdapter) -> Plan`

- `enquiry_text: str` — the raw, unstructured lead enquiry, verbatim.
- `tool_manifest: list[dict]` — generated by `tools/registry.tool_manifest()`, **never
  hand-written**, so the Planner's view of available tools can never drift from what the Executor
  can actually run.

JSON example (one manifest entry, from `Tool.manifest_entry()`):

```json
{
  "name": "lookup_jurisdiction_rule",
  "description": "Deterministic lookup against a local rules file, returns the handling rule for a country.",
  "args_schema": {
    "title": "LookupJurisdictionRuleArgs",
    "type": "object",
    "properties": { "country": { "type": "string" } },
    "required": ["country"]
  }
}
```

### Output

`Plan` (`server/app/schemas/plan.py`):

```json
{
  "steps": [
    {
      "step": 1,
      "tool": "parse_enquiry",
      "args": { "enquiry_text": "..." },
      "rationale": "Extract structured fields before anything else can run."
    },
    {
      "step": 2,
      "tool": "lookup_jurisdiction_rule",
      "args": { "country": "Singapore" },
      "rationale": "Need the jurisdiction rule before scoring."
    },
    {
      "step": 3,
      "tool": "score_lead",
      "args": { "extracted": "...", "jurisdiction_rule": "..." },
      "rationale": "Score using extracted fields and jurisdiction rule."
    },
    {
      "step": 4,
      "tool": "write_record",
      "args": { "extracted": "...", "jurisdiction_rule": "...", "score": "..." },
      "rationale": "Persist the final record."
    }
  ]
}
```

### Validation rules

- `PlanStep.step: int`, `ge=1` — 1-indexed position.
- `PlanStep.tool: ToolName` — a closed enum (`parse_enquiry | lookup_jurisdiction_rule |
  score_lead | write_record`); the Planner **cannot** invent a tool name, Pydantic rejects
  anything outside the enum at parse time.
- `PlanStep.rationale: str`, `min_length=1` — required, read by the Verifier's plan-deviation
  check, never executed.
- `Plan.steps: list[PlanStep]` — no length/order constraint enforced by the schema itself.
- **Deterministic, non-LLM policy guardrail** (documented in `docs/architecture.md` §6/§15, not
  yet implemented — tracked as a TODO on `Plan` itself): mandatory tools (`lookup_jurisdiction_rule`,
  `score_lead`) must each appear exactly once, checked in code, never left to model judgment. This
  guardrail is the primary defense against prompt injection making the Planner omit a required
  step.
- Response is obtained via `adapter.complete_structured(..., response_schema=Plan)` — see §5 for
  the adapter's own retry contract.

### Failure modes

| Failure | Behavior |
|---|---|
| Schema validation failure (malformed JSON / wrong types / invalid enum value) | Adapter retries internally at most once (§5). The **first-attempt outcome is still counted** toward the harness's planner schema-breach-rate metric regardless of whether the retry recovers it — never silently absorbed. |
| Guardrail violation (mandatory tool missing/duplicated) once implemented | Must be caught in code, not by the model; caller should treat this the same as a schema failure for reporting purposes. |
| Adapter/provider error (timeout, rate limit, auth) | Propagates as an `LLMProviderError` (or provider-specific exception) to the Orchestrator; not silently swallowed here. |

## 2. Executor

**Purpose:** Deterministically carry out a validated `Plan` via real tool/function calls and
assemble the final record. The Executor is **not an LLM call** and contains no LLM calls of its
own (`docs/development-rules.md`: "Executor is deterministic"); `tools/parse_enquiry.py` happens
to be LLM-backed internally, but that call is opaque to the Executor's control flow.

### Input

`run_plan(plan: Plan, enquiry_text: str, registry: ToolRegistry) -> ExecutionResult`

- `plan: Plan` — the validated output of §1, iterated in `steps` order — the Executor cannot
  itself skip/reorder/substitute a step; it is literally "iterate `plan.steps`".
- `enquiry_text: str` — the original raw text, passed through to tools that need it (e.g.
  `parse_enquiry`).
- `registry: ToolRegistry` — **additive parameter**, not in the original two-argument sketch of
  this contract. Justification: the Executor must use `ToolRegistry` for *all* tool lookup and
  must never import a concrete `Tool` subclass (development-rules.md), so it needs a registry
  instance from somewhere; since `ToolRegistry` itself needs a `ModelAdapter` (for
  `parse_enquiry`), the only alternative would be for `run_plan()` to construct that adapter
  itself — which would make the Executor responsible for LLM-provider wiring (contradicting "the
  Executor contains no LLM calls of its own") and impossible to exercise with mock tools in tests.
  Passing `registry` in keeps the Executor a pure function of its inputs and fully testable with
  a fake or mock-populated registry.

### Output

`ExecutionResult` (`server/app/agent/executor.py`):

```json
{
  "trace": {
    "calls": [
      {
        "step": 1,
        "tool": "parse_enquiry",
        "args": { "enquiry_text": "..." },
        "status": "success",
        "result": { "name": "Jane Doe", "email": "jane@example.com", "budget_band": "high" },
        "error": null,
        "validation_errors": null,
        "latency_ms": 842.1,
        "started_at": "2026-07-31T02:10:00.000Z",
        "finished_at": "2026-07-31T02:10:00.842Z"
      }
    ]
  },
  "final_record": {
    "extracted": { "name": "Jane Doe", "email": "jane@example.com" },
    "jurisdiction_rule": { "country": "Singapore", "requires_disclaimer": true, "restricted": false, "handling_note": "..." },
    "score": 78,
    "score_breakdown": { "budget": 40, "urgency": 20, "jurisdiction_risk": 18 },
    "dedupe_hash": "a3f5c9d1..."
  },
  "error": null
}
```

`ToolCall.validation_errors` and `ToolCall.started_at`/`finished_at` are **additive fields**
(`server/app/schemas/tool_trace.py`) added during Executor implementation: the task requires every
tool execution to record start time, end time, and validation errors as structured data, which the
original `ToolCall` shape (only `latency_ms` + a free-text `error`) could not carry.
`validation_errors` is populated only when `status="error"` was caused by a `ToolValidationError`
(the raw `.errors` list); it is `null` for controlled business failures and unexpected exceptions,
which are still fully described by the free-text `error` field.

### Validation rules

- For each `PlanStep`: look up the tool by its enum-constrained name via `ToolRegistry.get_tool()`
  (§4) — **never** by parsing free-form model text.
- `step.args` is validated against *that tool's own* `args_schema` by `Tool.execute()` (§4) — a
  distinct check from the Plan's own schema validation — before the tool's `run()` is ever called,
  catching planner-hallucinated arguments before they reach real execution.
- Every step, success or failure, produces exactly one `ToolCall` entry in `trace.calls` with
  `status` (`ToolCallStatus.SUCCESS` / `.ERROR`), `result` or `error`, a measured `latency_ms`, and
  `started_at`/`finished_at` timestamps. The trace accumulates in step order and is returned
  as-is even when execution stops early, so it is always complete up to (and including) the
  failing step.
- `final_record` is only populated when every step in the plan succeeds **and** the plan included
  all four canonical tools (`parse_enquiry`, `lookup_jurisdiction_rule`, `score_lead`,
  `write_record`) — a plan that omits one is not an error, it simply yields `final_record: null`.
- Execution stops at the first failure of any kind; the only way a step goes unexecuted is that an
  earlier one already failed and halted the loop — the Executor never itself skips a step for any
  other reason.

### Error behavior

Three distinct failure categories are recognized, each converted into the same structured
`ExecutionResult(error=...)` shape — `run_plan()` never raises on a tool's behalf, so the pipeline
never crashes and the trace built so far is always returned intact:

| Failure category | Cause | Behavior |
|---|---|---|
| **Tool validation failure** | `Tool.execute()` raises `ToolValidationError` — malformed/hallucinated `step.args`, or a buggy `run()` returning a malformed successful result. | Recorded with `status="error"`, structured `validation_errors`, execution stops. |
| **Controlled tool failure** | `Tool.execute()` returns normally with `ToolResult(success=False, error=...)` (e.g. `write_record` duplicate) — an expected business outcome, not a bug. | Recorded with `status="error"`, `error` set from `ToolResult.error`, `validation_errors=null`, execution stops. |
| **Unexpected internal exception** | Anything else raised out of `Tool.execute()` — a tool bug (e.g. today's placeholder `NotImplementedError`), a provider timeout inside `parse_enquiry`, or an unknown tool name from the registry. | Logged loudly at ERROR with a full traceback (so it is never silently swallowed), then recorded with `status="error"`, `error=f"{type}: {message}"`, execution stops — the exception itself never propagates out of `run_plan()`. |
| Any deviation from the plan (a step skipped/reordered/substituted) | Cannot originate from the Executor itself (it only iterates `plan.steps`) — if the Verifier detects one, it necessarily traces back to a compromised Plan or an Executor bug, which is exactly why the Verifier checks trace-vs-plan independently. | — |

## 3. Verifier

**Purpose:** Independently judge whether a completed run's `final_record` is trustworthy —
without trusting the Planner's or Executor's own reasoning. The Verifier is **completely
independent** (`docs/development-rules.md`): its own module, its own prompt file, no shared
context/message-history/prompt text with the Planner or `parse_enquiry`, and it issues its own
fresh, stateless LLM call — never a self-check appended to a prior call.

### Input

`verify(enquiry_text: str, plan: Plan, tool_call_trace: ToolCallTrace, final_record: dict, adapter: ModelAdapter) -> VerifierDecision`

- `enquiry_text` — the original raw text (primary evidence for fabrication checks).
- `plan` — what was *intended*.
- `tool_call_trace` — what *actually ran*.
- `final_record` — the assembled record to be judged.
- Deliberately **excludes** the Planner's/extractor's rationale beyond what's already visible in
  `plan`/`tool_call_trace` — the Verifier must re-derive judgments from primary evidence, not
  borrow the upstream stages' justification.

### Output

`VerifierDecision` (`server/app/schemas/verifier.py`):

```json
{
  "pass": true,
  "confidence": 0.92,
  "fabrication_detected": false,
  "fabricated_fields": [],
  "plan_deviation_detected": false,
  "deviation_details": null,
  "reason": "All record fields are present or directly inferable in the enquiry text; tool trace matches the plan exactly."
}
```

Failing example:

```json
{
  "pass": false,
  "confidence": 0.81,
  "fabrication_detected": true,
  "fabricated_fields": ["phone"],
  "plan_deviation_detected": false,
  "deviation_details": null,
  "reason": "Phone number in final_record does not appear anywhere in enquiry_text and appears fabricated."
}
```

### PASS/FAIL semantics

- `passed` (serialized as `"pass"` via a Pydantic field alias — `populate_by_name=True` so both
  `passed=` and `pass=` work when constructing in code) is the single gate: `True` →
  `final_status="completed"`; `False` → routes to the Repair Loop (§10), and if repair also fails,
  `final_status="quarantined"` — **never silently dropped**.
- Two distinct failure classes must genuinely be checked, per the brief:
  1. **Fabrication** — any `final_record` field not present/inferable in `enquiry_text` →
     `fabrication_detected=true`, offending field names listed in `fabricated_fields`.
  2. **Plan deviation** — any skip/reorder/substitution between `plan.steps` and
     `tool_call_trace.calls` → `plan_deviation_detected=true`, human-readable detail in
     `deviation_details`.
- `reason` must be non-empty whenever `passed` is `False` (documented contract; enforcement via a
  `model_validator` is a currently-open TODO on the schema — see the file — but the *rule* is
  fixed regardless of when the validator lands).
- `confidence: float`, constrained `0.0 ≤ confidence ≤ 1.0`.

### Failure modes

| Failure | Behavior |
|---|---|
| Verifier LLM call schema-invalid | Same adapter-level retry-once contract as §5/§1; first-attempt outcome still counted for the harness. |
| `passed=False` with empty `reason` | Contract violation — must never happen once the validator above is implemented; treat as a bug, not a valid decision, if seen. |
| Verifier and Planner/Extractor share a systematic blind spot (same model family) | Not detectable from the contract alone — mitigated by allowing a distinct `VERIFIER_MODEL` (see `Settings.resolved_model("verifier")`), documented as a **partial** mitigation only (`docs/architecture.md` §15). |

## 4. Tool interface

**Purpose:** One common contract every tool (LLM-backed or deterministic) implements, so the
Executor can dispatch to any of them uniformly and the Planner's manifest can never drift from
what actually runs. Defined in `server/app/tools/base.py`. Subclassing `Tool` auto-registers the
class (`Tool.__init_subclass__`); `tools/registry.py`'s `ToolRegistry` builds instances from the
registered classes and is the only place a `Tool` gets constructed for real use (§2, §6).

Every tool exposes `name`, `description`, `args_schema`, `result_schema` (class attributes), and
three methods: the abstract `run()` (business logic) plus two concrete, non-overridable methods
the base class provides for free — `execute()` and `manifest_entry()`:

| Method | Kind | Purpose |
|---|---|---|
| `execute(raw_args) -> ToolResult` | concrete, on `Tool` | The single sanctioned entry point: validate → `run()` → validate. |
| `run(args: BaseModel) -> ToolResult` | abstract, per-tool | The tool's actual work, against already-validated `args`. |
| `manifest_entry() -> dict` | concrete classmethod, on `Tool` | JSON-serializable `{name, description, args_schema}` for the Planner. |
| `validate_args(raw_args) -> BaseModel` / `validate_result(data) -> BaseModel` | concrete, on `Tool` | Used internally by `execute()`; also callable directly. |

### `execute()`

```python
def execute(self, raw_args: dict[str, Any] | BaseModel) -> ToolResult: ...
```

- **Purpose:** the only way a tool should be invoked. Validates `raw_args` against `args_schema`,
  calls `run()` with the validated model, and — only when `run()` reports success — validates the
  returned `data` against `result_schema` too. This is "complete validation": both sides of the
  boundary are checked, and `run()` implementations never need to re-validate what they were given.
- JSON example of a successful call's return value (`ToolResult`, a dataclass):

```json
{
  "success": true,
  "data": { "lead_id": "b2e1...", "dedupe_hash": "a3f5c9d1..." },
  "error": null,
  "latency_ms": 12.4
}
```

- **Validation rules:** raises `ToolValidationError(tool_name, errors)` — never a bare Pydantic
  `ValidationError` — if `raw_args` don't match `args_schema`, or if a *successful* result's `data`
  doesn't match `result_schema`. Skips result validation entirely when `result.success is False`
  (an expected business failure's `data` is `None` by convention, not something to validate).
- **Failure modes:** `ToolValidationError` for malformed/hallucinated input or a buggy `run()`
  returning the wrong result shape (a framework-level contract violation); `run()`'s own
  `NotImplementedError` (current scaffold stage) or business-logic exception otherwise.

### `run()`

```python
def run(self, args: BaseModel) -> ToolResult: ...
```

- **Purpose:** execute the tool against already-validated `args` (guaranteed valid by `execute()`
  — never called directly by the Executor).
- **Validation rules:** must not raise for *expected* business failures (e.g. duplicate lead) —
  return `ToolResult(success=False, error=...)` instead, so the Executor can act on it
  deterministically. Unexpected exceptions must still propagate (loudly), never be swallowed.
- **Failure modes:** `success=False` with a human-readable `error` string for expected failures
  (duplicate dedupe hash, unknown jurisdiction, adapter error inside `parse_enquiry`); an
  unhandled exception for genuine bugs. At the current scaffold stage, every tool's `run()` simply
  `raise NotImplementedError` once `execute()` has already validated the input — no business logic.

### `manifest_entry()`

```python
@classmethod
def manifest_entry(cls) -> dict[str, Any]: ...
```

- **Purpose:** JSON-serializable `{name, description, args_schema}` handed to the Planner — derived
  directly from `args_schema.model_json_schema()` so the Planner's view can never drift from what
  `run()` actually accepts. A classmethod: needs no instance, so `ToolRegistry.tool_manifest()` can
  build the full manifest from registered *classes* alone, with no dependencies (e.g. no
  `ModelAdapter`) required.
- JSON example: see the `lookup_jurisdiction_rule` manifest entry under §1.
- **Validation rules:** `args_schema` and `result_schema` are both Pydantic `BaseModel` subclasses
  (per-tool: `ParseEnquiryArgs`/`ExtractedFields`, `LookupJurisdictionRuleArgs`/`JurisdictionRule`,
  `ScoreLeadArgs`/`ScoreLeadResult`, `WriteRecordArgs`/`WriteRecordResult`) — enforced at
  class-definition time by `Tool.__init_subclass__`, which raises `TypeError` immediately if a
  subclass sets `args_schema`/`result_schema` to anything else, or omits `name`/`description`.
- **Failure modes:** if a tool's `args_schema` changes shape without updating the Planner's prompt,
  the Planner may produce args that fail validation at `execute()` time — caught by `execute()`'s
  input validation, not a manifest-level failure.

### Automatic registration

- **Purpose:** merely defining a `Tool` subclass (in a module that gets imported — see
  `tools/registry.py`'s explicit imports of the four tool modules) is the only step needed for a
  tool to appear in the manifest and be dispatchable by name; there is no hand-maintained list to
  keep in sync.
- **Validation rules:** `Tool.__init_subclass__` rejects (raises `TypeError`) a concrete subclass
  missing `name`/`description`/`args_schema`/`result_schema`, or with a non-`BaseModel` schema;
  raises `ValueError` on a duplicate `name` across two different classes. Subclasses that don't yet
  override `run()` (e.g. a hypothetical intermediate base) are silently skipped, not registered.
- **Failure modes:** a second tool file accidentally reusing an existing `name` fails loudly at
  import time (`ValueError: Duplicate tool name ...`), not silently overwritten in the registry.

### Registered tools

| Tool | Type | `args_schema` → `result_schema` |
|---|---|---|
| `parse_enquiry` | LLM-backed | `ParseEnquiryArgs{enquiry_text}` → `ExtractedFields{name, email, phone, country, budget_band, asset_interest, urgency}` |
| `lookup_jurisdiction_rule` | Deterministic | `LookupJurisdictionRuleArgs{country}` → `JurisdictionRule{country, requires_disclaimer, restricted, handling_note}` |
| `score_lead` | Deterministic, pure function | `ScoreLeadArgs{extracted, jurisdiction_rule}` → `ScoreLeadResult{score, breakdown}` |
| `write_record` | Deterministic | `WriteRecordArgs{extracted, jurisdiction_rule, score}` → `WriteRecordResult{lead_id, dedupe_hash}` |

### `ToolRegistry`

**Purpose:** builds one ready-to-use instance of every auto-registered `Tool` subclass, wiring in
shared dependencies (currently just a `ModelAdapter`, for `parse_enquiry`) by introspecting each
tool class's `__init__` signature. Defined in `server/app/tools/registry.py`.

| Member | Signature | Purpose |
|---|---|---|
| `ToolRegistry(*, adapter=None)` | constructor | Eagerly instantiates every registered tool class; fails fast (`ToolRegistryError`) if a tool needs a dependency that wasn't provided. |
| `get_tool(name: str) -> Tool` | instance method | Dispatch by name for the Executor (§2) — `KeyError` on an unknown name. |
| `tool_manifest() -> list[dict]` | **staticmethod** | The Planner's manifest, sorted by `name` — deterministic regardless of import order, and callable with zero dependencies. |

- **Validation rules:** `ToolRegistry()` (no `adapter`) succeeds only if every registered tool's
  `__init__` needs no dependency it doesn't have; today that means it fails for `parse_enquiry`
  specifically, and `ToolRegistry(adapter=...)` is required for a fully usable registry.
- **Failure modes:** `ToolRegistryError` at construction time (not at first `get_tool()` call) when
  a dependency is missing — a configuration error, not a per-request failure.

## 5. LLM Adapter interface

**Purpose:** One provider-agnostic contract (`server/app/llm/base.py`) so Planner, Executor's
`parse_enquiry` tool, and Verifier never depend on a concrete provider class — the model can be
swapped via `MODEL_PROVIDER` without touching pipeline code. `server/app/llm/factory.py` is the
*only* place in the codebase permitted to import a concrete adapter class.

### `complete_structured()`

```python
def complete_structured(self, request: StructuredCompletionRequest) -> StructuredCompletionResponse: ...
```

Input — `StructuredCompletionRequest` (dataclass):

```json
{
  "system_prompt": "You are a careful data extraction assistant...",
  "user_prompt": "Extract structured fields from: ...",
  "response_schema": "ExtractedFields",
  "model": "gpt-4o-mini",
  "temperature": 0.0,
  "tools": null,
  "metadata": { "run_id": "b2e1...", "stage": "parse_enquiry" }
}
```

Output — `StructuredCompletionResponse` (dataclass):

```json
{
  "parsed": { "name": "Jane Doe", "email": "jane@example.com", "budget_band": "high" },
  "raw_response": { "id": "chatcmpl-...", "usage": { "prompt_tokens": 210, "completion_tokens": 48 } },
  "prompt_tokens": 210,
  "completion_tokens": 48,
  "latency_ms": 842.1,
  "model": "gpt-4o-mini"
}
```

### Validation rules

- `parsed` must validate against `request.response_schema` — the adapter retries **internally at
  most once** on schema-validation failure before giving up.
- Every call is stateless: **never carries conversation history across calls**
  (`docs/development-rules.md`: "Each LLM call is isolated") — a fresh `StructuredCompletionRequest`
  per call, no hidden shared state between Planner/Verifier/repair calls.
- `raw_response` is kept verbatim for durable logging (`llm_calls.raw_response` — §8), not
  discarded after parsing.
- `prompt_tokens`/`completion_tokens`/`latency_ms` are measured at the call site, never estimated
  after the fact.

### Failure modes

| Failure | Behavior |
|---|---|
| Schema validation fails on both the original attempt and the one internal retry | Adapter surfaces this to the caller (exact exception type is provider/implementation-specific); the caller (Planner/Verifier/`parse_enquiry`) is responsible for counting the **first-attempt** outcome toward the harness's schema-breach-rate metric regardless of the retry's outcome. |
| Provider error (timeout, rate limit, auth failure) | Must propagate as an `LLMProviderError` (or equivalent) rather than a bare provider SDK exception, so `main.py`'s central exception handler can map it to a structured JSON error body with the correlating `run_id`. |
| No concrete adapter implemented for the configured `MODEL_PROVIDER` (current scaffold state) | `llm/factory.build_adapter()` raises `NotImplementedError` naming the missing provider — this is an infra/config error, not a runtime data contract violation. |
| Local model (e.g. via Ollama) without guaranteed JSON-schema support | Expected to fall back to instruct-then-validate-then-retry and have a *higher* schema-breach rate — must be reported honestly, not tuned away. |

## 6. Repository interface

**Purpose:** The single place all reads/writes to `runs`, `llm_calls`, `leads`, and
`harness_batches` go through (`server/app/db/repository.py`) — so persistence logic isn't
duplicated across `api/` and `agent/`, and so SQLite could later be swapped for Postgres by
changing this module alone.

| Function | Signature | Purpose |
|---|---|---|
| `create_run` | `(db: Session, run: RunResult, *, harness_batch_id: str \| None = None) -> Run` | Map a `RunResult` (§ below) to a `Run` ORM row (+ its `LlmCall` children), insert, commit, return the persisted row. `harness_batch_id` is optional because `RunResult` itself doesn't carry it (a single run doesn't know which batch it belongs to); passing it links the row without a separate update call. |
| `get_run` | `(db: Session, run_id: str) -> Run \| None` | Fetch a single run by id. |
| `list_runs` | `(db: Session, *, limit: int = 50, offset: int = 0) -> list[Run]` | Paginated list, most recent first. |
| `find_lead_by_dedupe_hash` | `(db: Session, dedupe_hash: str) -> Lead \| None` | Used by `tools/write_record.py`'s duplicate check. |
| `create_lead` | `(db: Session, **fields) -> Lead` | Insert a new lead row. |
| `list_leads` | `(db: Session, *, status: str \| None = None) -> list[Lead]` | Optionally filter by `accepted`/`quarantined`. |
| `create_harness_batch` | `(db: Session, **fields) -> HarnessBatch` | Insert a new harness batch row. |
| `get_latest_harness_batch` | `(db: Session) -> HarnessBatch \| None` | Backs `GET /api/harness/summary`. |
| `get_harness_batch` | `(db: Session, harness_batch_id: str) -> HarnessBatch \| None` | **Additive** (Evaluation Harness task): fetch a specific batch by id, so an interrupted harness run can be resumed by id rather than only by "whatever is latest". |
| `find_run_by_batch_position` | `(db: Session, harness_batch_id: str, enquiry_id: str, repeat_index: int) -> Run \| None` | **Additive** (Evaluation Harness task): backs the harness's resumability check -- has this `(enquiry_id, repeat_index)` pair already run *within this batch*? Scoped by `harness_batch_id` as well, since the same pair may legitimately also exist in a different batch or as a one-off live run. |
| `list_runs_for_batch` | `(db: Session, harness_batch_id: str) -> list[Run]` | **Additive** (Evaluation Harness task): every run belonging to one batch, oldest first -- the raw material `evaluation/metrics.py` aggregates. |
| `finish_harness_batch` | `(db: Session, harness_batch_id: str, *, metrics: dict) -> HarnessBatch` | **Additive** (Evaluation Harness task): stamps `finished_at`/`metrics` once all runs in the batch are done -- the "close out" counterpart to `create_harness_batch`'s "open" call. |

### JSON example

Input to `create_run` (a `RunResult`, abbreviated — full shape in §8's `RunResult` schema):

```json
{
  "id": "b2e1c4a0-...",
  "enquiry_text": "Hi, I'm interested in whisky cask investment...",
  "final_status": "completed",
  "verifier_decision": { "pass": true, "confidence": 0.92, "reason": "..." },
  "total_tokens": 1180,
  "total_cost_usd": 0.0031
}
```

Output of `create_lead` (a `Lead` ORM row, conceptually):

```json
{
  "id": "d4f8...",
  "dedupe_hash": "a3f5c9d1...",
  "email": "jane@example.com",
  "status": "accepted",
  "source_run_id": "b2e1c4a0-..."
}
```

### Validation rules

- `create_run`/`create_lead`/`create_harness_batch` never partially commit: either the full row
  (+ children, for `create_run`) is persisted, or the call raises and nothing is written.
- `find_lead_by_dedupe_hash` is the **only** sanctioned way to check for duplicates before
  `create_lead` — no ad hoc queries elsewhere in `tools/write_record.py` or `agent/`.
- Query functions (`get_run`, `list_runs`, `list_leads`, `get_latest_harness_batch`) never mutate
  state.
- `Run.model_provider`/`model_name` (top-level columns, §8) have no direct `RunResult` field —
  `create_run` takes them from the *first* entry in `run.llm_calls` (conventionally the planner
  call), or leaves them `None` if there were no LLM calls at all (e.g. an early executor failure).
  This is a repository-level mapping decision, not a schema change.

### Failure modes

| Failure | Behavior |
|---|---|
| `get_run`/`find_lead_by_dedupe_hash`/`get_latest_harness_batch`/`get_harness_batch`/`find_run_by_batch_position` — no matching row | Return `None`, never raise. |
| `create_lead` called with a `dedupe_hash` that already exists | The `leads.dedupe_hash` unique constraint (§8) raises an `IntegrityError` at the DB layer — callers (`tools/write_record.py`) must check via `find_lead_by_dedupe_hash` *first* and treat a duplicate as an expected `ToolResult(success=False, error="duplicate")`, not rely on catching the DB exception. |
| `create_run` called with a `RunResult` referencing an unknown `harness_batch_id` | FK constraint violation — the caller (harness/orchestrator) is responsible for creating the `HarnessBatch` row first. |
| `finish_harness_batch` called with an unknown `harness_batch_id` | Raises `ValueError` — the caller must have created the batch first via `create_harness_batch`. |

### Validation rules

- Request bodies validated against Pydantic models by FastAPI at the boundary — malformed input
  never reaches route logic.
- Response models are asserted by FastAPI (`response_model=...`) against the exact `schemas/`
  classes — a route cannot silently return a shape that violates the contract.
- No CORS configuration — single-origin deployment (`docs/architecture.md` §3/§13); routes assume
  same-origin requests from the built React app or local dev's Vite proxy.
- `GET /api/leads?status=...` — `status` must be one of `accepted | quarantined` when provided
  (enforced by whatever validates against `Lead.status`, §8).

| Failure | Response |
|---|---|

| Malformed request body | FastAPI's standard `422 Unprocessable Entity` with field-level detail. |

## 8. Database entities

**Purpose:** The persisted, durable record of every run, LLM call, lead, and harness batch — the
primary observability artifact (`docs/architecture.md` §12: "durable trace in SQLite ... is the
primary observability artifact, since it survives restarts"). Defined in
`server/app/db/models.py`; JSON columns store the corresponding Pydantic schema's `.model_dump()`
output verbatim.

### `runs`

**Purpose:** one row per pipeline execution (live API request or one of the harness's 45 runs).

```json
{
  "id": "b2e1c4a0-...",
  "enquiry_text": "Hi, I'm interested in...",
  "enquiry_id": "enq-07",
  "repeat_index": 2,
  "is_adversarial": false,
  "plan": { "steps": [ /* ... */ ] },
  "plan_schema_valid": true,
  "tool_call_trace": { "calls": [ /* ... */ ] },
  "final_record": { /* ... */ },
  "verifier_pass": true,
  "verifier_confidence": 0.92,
  "verifier_reason": "...",
  "fabrication_detected": false,
  "fabricated_fields": [],
  "plan_deviation_detected": false,
  "deviation_details": null,
  "repair_attempted": false,
  "repair_succeeded": null,
  "final_status": "completed",
  "total_tokens": 1180,
  "total_cost_usd": 0.0031,
  "total_latency_ms": 2140.5,
  "model_provider": "openai",
  "model_name": "gpt-4o-mini",
  "harness_batch_id": null,
  "notes": null,
  "created_at": "2026-07-31T00:00:00Z"
}
```

**Validation rules:** `id` PK (UUID default); `final_status` ∈ `{completed, quarantined, error}`;
`harness_batch_id` FK → `harness_batches.id`, nullable (null for live API runs);
`fabricated_fields`/`deviation_details` complete the model's coverage of `VerifierDecision` (§3),
which already includes both — added so the DB row never silently drops verifier evidence the
harness's fabrication-rate analysis needs; both nullable, both `null`/`[]` when no verifier ran.
Indexed on `(enquiry_id, repeat_index)` to back the harness's resumability check (§ below,
`harness_batches` failure modes) and on `harness_batch_id`.

**Failure modes:** inserting with a `harness_batch_id` that doesn't exist → FK integrity error
(caller must create the batch row first, §6).

### `llm_calls`

**Purpose:** fine-grained per-call log for observability/cost breakdown; one row per LLM call made
during a run (planner, `parse_enquiry`, verifier, and any repair-stage re-calls).

```json
{
  "id": "c7a1...",
  "run_id": "b2e1c4a0-...",
  "stage": "planner",
  "prompt_tokens": 340,
  "completion_tokens": 120,
  "cost_usd": 0.0009,
  "latency_ms": 610.2,
  "model_provider": "openai",
  "model_name": "gpt-4o-mini",
  "raw_request": { "system_prompt": "...", "user_prompt": "..." },
  "raw_response": { "id": "chatcmpl-...", "usage": { "...": "..." } },
  "created_at": "2026-07-31T00:00:00Z"
}
```

**Validation rules:** `stage` ∈ `{planner, parse_enquiry, verifier, repair_planner,
repair_verifier}`; `run_id` FK → `runs.id`, required (every `LlmCall` belongs to exactly one run).

**Failure modes:** `run_id` referencing a non-existent run → FK integrity error; this table is
append-only in normal operation (no update/delete path defined).

### `leads`

**Purpose:** an accepted or quarantined lead record — the output the business actually cares
about, one row per successfully executed (or repaired) `write_record` call.

```json
{
  "id": "d4f8...",
  "dedupe_hash": "a3f5c9d1...",
  "name": "Jane Doe",
  "email": "jane@example.com",
  "phone": "+65 5551234",
  "country": "Singapore",
  "budget_band": "high",
  "asset_interest": "single malt whisky casks",
  "urgency": "medium",
  "score": 78,
  "score_breakdown": { "budget": 40, "urgency": 20, "jurisdiction_risk": 18 },
  "jurisdiction_rule": { "country": "Singapore", "requires_disclaimer": true, "restricted": false, "handling_note": "..." },
  "status": "accepted",
  "source_run_id": "b2e1c4a0-...",
  "created_at": "2026-07-31T00:00:00Z"
}
```

**Validation rules:** `dedupe_hash` **unique** (SHA-256 of normalized email/phone, per
`tools/write_record.py`) — this is the sole duplicate-detection mechanism; `status` ∈ `{accepted,
quarantined}`; `source_run_id` FK → `runs.id`, nullable.

**Failure modes:** insert with a `dedupe_hash` already present → unique constraint violation
(`IntegrityError`) — must be pre-checked via `find_lead_by_dedupe_hash` (§6), not relied upon as
the primary control flow signal.

### `harness_batches`

**Purpose:** one row per full evaluation harness execution (`python -m evaluation.harness`),
aggregating the 45 runs it produced.

```json
{
  "id": "e9c2...",
  "started_at": "2026-07-31T00:00:00Z",
  "finished_at": "2026-07-31T00:14:32Z",
  "n_runs": 45,
  "metrics": {
    "completion_rate": 0.93,
    "planner_schema_breach_rate": 0.02,
    "fabrication_rate": 0.04,
    "verifier_catch_rate": 1.0,
    "tool_selection_accuracy": 0.98,
    "repair_success_rate": 0.6,
    "mean_tokens": 1180,
    "mean_cost_usd": 0.0031,
    "mean_latency_ms": 2140.5
  },
  "config_snapshot": { "model_provider": "openai", "model_name": "gpt-4o-mini" }
}
```

**Validation rules:** `n_runs` should equal the number of `runs` rows with this `id` as their
`harness_batch_id` once the batch is `finished_at`-stamped; `metrics`/`config_snapshot` are
free-form JSON by design (metric set is expected to evolve — see `evaluation/metrics.py`), but
`config_snapshot` must be captured at batch start so harness numbers stay reproducible
(`docs/architecture.md` §5, §11).

**Failure modes:** a batch left with `finished_at=null` indicates an interrupted harness run — the
harness is designed to be idempotent/resumable (skips already-completed `(enquiry_id,
repeat_index)` pairs) rather than treating this as corrupt state.

## Cross-cutting rules (apply to every contract above)

- **Structured outputs everywhere** (`docs/development-rules.md`) — every LLM-facing contract
  (Plan, ExtractedFields, VerifierDecision) is a Pydantic schema; no free-text parsing anywhere in
  the pipeline.
- **Each LLM call is isolated** — no contract in this document implies or permits carrying
  conversation history between Planner, `parse_enquiry`, Verifier, or repair-stage calls.
- **Tool contracts are stable** — `args_schema`/`result_schema` for the four tools in §4 are the
  single source of truth for both the Planner's manifest and the Executor's validation; changing
  one without the other drifting is exactly the failure this document exists to prevent.
- **Never silently drop a run** — every pipeline execution ends in exactly one of
  `completed | quarantined | error` on the `runs` row; there is no code path that discards a run
  without a `final_status` and (for `quarantined`) a `verifier_reason`.
